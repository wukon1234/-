# 第五章 系统实现

本章详细介绍商城智能购物助手系统的具体实现过程，包括开发环境配置、核心模块的实现、关键技术的应用以及系统界面展示等内容。系统采用前后端分离的架构设计，后端基于Spring Boot框架构建，前端基于Vue 3框架构建，通过RESTful API进行数据交互，智能助手模块采用RAG技术和LLM服务实现智能问答功能。

## 5.1 开发环境配置

### 5.1.1 后端环境配置

**（1）项目依赖配置**

后端项目使用Maven进行依赖管理，通过在pom.xml文件中声明项目依赖，Maven会自动下载和管理所需的JAR包。核心依赖及其作用说明如下：

Spring Boot Web依赖提供了完整的Web服务能力，包括RESTful API的构建、请求处理、响应封装等功能。该依赖内置了Tomcat服务器，无需额外配置应用容器即可直接运行Web应用。

MyBatis Plus依赖是MyBatis的增强工具，提供了更便捷的数据库操作能力。该依赖封装了常见的CRUD操作，支持Lambda表达式查询、条件构造器、 分页插件等功能，大大简化了数据库操作的代码编写量。在本系统中，MyBatis Plus版本指定为3.5.3，以确保与Spring Boot 2.7.x版本的兼容性。

MySQL驱动依赖用于连接MySQL数据库，JDBC驱动负责建立Java应用程序与MySQL服务器之间的连接通道。MySQL Connector/J是MySQL官方提供的JDBC驱动实现，支持数据库连接池和连接管理功能。

JWT（JSON Web Token）依赖用于生成和验证JSON格式的令牌。jjwt库提供了JWT的签发、验证和解析功能，系统通过JWT实现用户身份认证和会话管理。在本系统中，JWT版本指定为0.9.1，该版本与Spring Boot 2.x系列具有较好的兼容性。

Lombok依赖是一个Java代码生成工具，通过注解自动生成Getter、Setter、构造器、Builder模式等代码，减少样板代码的编写。在本系统中，Lombok主要用于实体类的定义，配合IDE插件使用可以显著提升开发效率。

**（2）应用配置文件**

系统使用application.yml作为应用配置文件，采用YAML格式编写，相比传统的properties文件具有更好的可读性和层次结构。配置文件主要包含以下配置项：

服务器端口配置指定系统运行时的HTTP服务端口，本系统配置为8080端口。前端开发服务器通过代理将API请求转发至该端口，实现前后端联调。

数据库连接配置包括连接URL、用户名、密码和驱动类名。连接URL指定了数据库的地址、端口和数据库名称，本系统使用的数据库名称为mall_assistant。用户名和密码用于数据库身份验证，确保应用具有正确的数据库访问权限。驱动类名指定了JDBC使用的数据库驱动实现。

MyBatis Plus配置指定了Mapper接口的XML映射文件位置为classpath:mapper/*.xml，并开启了下划线命名转驼峰命名的自动转换功能。这一配置使得数据库字段（如user_name）可以自动映射到Java实体类属性（如userName），简化了属性映射的配置工作。

JWT配置包括密钥secret和过期时间expiration两个关键配置项。密钥用于JWT令牌的签名验证，过期时间以毫秒为单位指定，本系统配置为86400000毫秒，即24小时。生产环境中密钥应使用复杂的随机字符串，并妥善保管以防止泄露。

LLM服务配置指定了大语言模型服务提供商为qwen（通义千问）以及API密钥。API密钥是调用通义千问服务的凭证，需要从阿里云百炼平台申请获取。

### 5.1.2 前端环境配置

**（1）项目初始化**

前端项目使用Vite作为构建工具，Vite是新一代的前端构建工具，相比Webpack具有更快的冷启动和热更新速度。项目创建时指定使用Vue 3和TypeScript模板，生成的项目结构包含src目录（源代码）、public目录（静态资源）、index.html（入口HTML）等标准目录和文件。

技术栈方面，Vue 3是当前最新的Vue主版本，采用了Composition API和响应式系统的重写，提供了更好的TypeScript支持和性能表现。TypeScript是JavaScript的超集，提供了静态类型检查和面向对象编程能力，能够在开发阶段发现潜在的类型错误，提高代码质量。Element Plus是基于Vue 3的UI组件库，提供了丰富的企业级UI组件，包括按钮、表单、表格、对话框等常用组件，能够快速构建美观的用户界面。

项目依赖安装完成后，需要额外安装Element Plus（UI组件库）、Pinia（状态管理库）、Axios（HTTP请求库）和Vue Router（路由管理库）。Pinia是Vue 3推荐的状态管理库，相比Vuex具有更简单的API和更好的TypeScript支持。Axios用于封装HTTP请求，Vue Router用于管理前端路由，实现单页应用的页面切换功能。

开发环境建议使用Node.js 16或更高版本，以支持ES Modules和现代JavaScript语法。包管理工具可以选择npm或pnpm，两者都能有效管理项目依赖。保持npm或pnpm版本与项目依赖要求一致，可以避免因工具版本差异导致的安装失败或构建异常。

在团队开发过程中，建议使用统一的代码风格和提交规范。ESLint用于检查代码语法和风格问题，Prettier用于代码格式化，两者配合使用可以确保团队成员的代码风格一致。Git commit hooks可以在提交前自动执行代码检查，避免不符合规范的代码进入版本库。

**（2）Vite配置**

前端项目通过vite.config.ts文件进行构建配置，该文件使用TypeScript编写，导出一个包含各种配置项的对象。

插件配置项指定了项目使用的Vite插件列表，vue()插件是开发Vue 3项目必需的配置，它负责处理.vue文件的解析和模板编译。

开发服务器配置包括端口号和代理设置。端口号配置为5173，这是Vite开发服务器的默认端口。代理配置将/api路径的请求转发至后端服务器，该配置解决了开发阶段的跨域问题，使得前端可以顺利调用后端API。配置中的target指定了后端服务的地址，changeOrigin设置为true可以修改请求头中的Origin字段，确保后端能够正确处理跨域请求。

路径别名配置将@符号映射到/src目录，简化了模块导入路径的书写。例如，原本需要写import xxx from '../../components/xxx'的导入语句，可以简写为import xxx from '@/components/xxx'，提高了代码的可读性和维护性。

在实际部署前，建议通过环境变量区分开发、测试和生产环境。前端可以使用.env.development和.env.production文件分别配置不同环境的参数，如API地址、日志级别和第三方服务开关等。这样当系统上线时，只需切换构建环境即可使用正确的配置，避免硬编码带来的配置管理和安全风险。

### 5.1.3 数据库初始化

系统通过执行SQL初始化脚本创建数据库和表结构。首先创建名为mall_assistant的数据库，指定字符集为utf8mb4（支持存储表情符号等四字节字符）和排序规则为utf8mb4_unicode_ci（基于Unicode编码的排序规则）。

用户表（user）用于存储用户基本信息，包含用户ID（主键自增）、用户名（唯一约束）、密码（加密存储）、邮箱、电话、头像、角色和状态等字段。用户名唯一约束确保不会出现重复用户名，角色字段用于区分普通用户和管理员，状态字段用于控制账户是否可用。

商品表（product）用于存储商品信息，包含商品ID（主键自增）、商品名称、描述、分类ID、价格（精确到小数点后两位）、库存、图片URL和状态等字段。价格字段使用DECIMAL类型确保金额计算的精确性，库存字段记录当前商品的可用数量，状态字段用于控制商品是否上架销售。

其他表结构还包括分类表、购物车表、订单表、订单项表、收货地址表、会话表和消息表等，这些表结构共同构成了系统的数据存储层，为各项业务功能的实现提供了数据支持。

## 5.2 用户认证模块实现

### 5.2.1 JWT工具类实现

系统实现了JwtUtil工具类，作为JWT令牌管理的核心组件。该工具类被Spring框架管理为一个Bean组件，可以在其他组件中通过依赖注入的方式使用。

JwtUtil工具类的主要功能包括三个方面：令牌生成、令牌解析和令牌验证。

令牌生成功能通过generateToken方法实现，该方法接收用户ID作为参数，使用JJWT库提供的方法构建JWT令牌。令牌的生成过程包括设置主题（用户ID）、签发时间、过期时间和签名算法。系统采用HS512算法进行签名，该算法具有较高的安全性，能够有效防止令牌被篡改。签名时使用的密钥从配置文件中读取，确保密钥的安全性和可配置性。

令牌解析功能通过getUserIdFromToken方法实现，该方法接收令牌字符串作为参数，使用JJWT库的方法解析令牌并提取其中的用户ID。解析过程中会验证签名的有效性，如果签名不合法会抛出异常。成功解析后返回令牌中包含的用户ID，供后续业务处理使用。

令牌验证功能通过validateToken方法实现，该方法接收令牌字符串作为参数，通过尝试解析令牌来验证其有效性。如果令牌格式正确、签名有效且未过期，返回true；否则返回false。该方法主要用于拦截器验证请求中的令牌，以及登录时验证令牌的有效性。

工具类通过@Value注解从配置文件读取jwt.secret和jwt.expiration两个配置项，实现了配置与代码的分离。这种设计使得密钥和过期时间可以独立修改，无需重新编译代码，提高了系统的可维护性和安全性。

### 5.2.2 JWT拦截器实现

系统实现了JwtInterceptor拦截器，用于验证请求中的JWT令牌，实现用户身份认证功能。拦截器实现了Spring MVC的HandlerInterceptor接口，在请求处理之前执行认证检查。

拦截器的验证流程如下：首先检查请求方法是否为OPTIONS请求，如果是则直接放行，因为浏览器的预检请求通常使用OPTIONS方法。然后从请求头中获取Authorization字段，检查其值是否以"Bearer "开头，如果不是则返回401未授权状态。接着提取令牌字符串，调用JwtUtil的validateToken方法验证令牌有效性，如果令牌无效同样返回401状态。最后从有效令牌中提取用户ID，将其存入请求属性中，供后续的处理方法使用。

拦截器验证失败时会向响应写入JSON格式的错误信息，包含状态码和错误消息。前端可以通过解析响应JSON获取错误原因，并提示用户进行相应的操作，如重新登录等。

拦截器配置在Spring MVC的注册配置中生效，可以指定需要拦截和需要放行的路径。通常需要放行的路径包括登录接口、注册接口和静态资源路径，而其他API接口都需要经过身份验证。

### 5.2.3 用户服务实现

系统实现了UserServiceImpl类，提供用户注册和登录功能的业务逻辑。该类继承自MyBatis Plus的ServiceImpl类，自动获得了基本的CRUD操作能力，并实现了自定义的UserService接口。

用户注册功能通过register方法实现，接收用户名和密码作为参数。注册流程首先检查用户名是否已存在，调用MyBatis Plus的条件查询方法查询数据库中是否存在同名用户，如果存在则返回错误信息。如果用户名可用，则创建新的用户对象，设置用户名、加密后的密码、默认角色和状态，然后保存到数据库。密码加密使用BCryptPasswordEncoder实现，该编码器采用BCrypt哈希算法，能够有效防止彩虹表攻击，安全性较高。注册成功后返回成功信息。

用户登录功能通过login方法实现，接收用户名和密码作为参数。登录流程首先查询用户名对应的用户记录，如果不存在则返回用户不存在的错误信息。如果用户存在，则使用BCryptPasswordEncoder验证密码是否匹配，如果不匹配则返回密码错误的错误信息。密码验证通过后，调用JwtUtil的generateToken方法生成JWT令牌，并将令牌和用户信息一起返回给前端。前端获取令牌后通常会存储在localStorage中，后续请求时携带在请求头中用于身份验证。

用户服务还提供了根据用户ID查询用户信息、修改用户资料等辅助功能，这些功能通过继承自ServiceImpl的方法或自定义查询方法实现。

## 5.3 商品模块实现

### 5.3.1 商品列表查询

系统实现了ProductController类，提供商品列表查询和商品详情获取两个核心接口。控制器使用@RestController注解标记为RESTful控制器，所有返回值会自动序列化为JSON格式。

商品列表查询接口通过list方法实现，支持分页查询、分类筛选和关键词搜索三个维度的查询条件。分页参数包括page（当前页码，默认1）和size（每页数量，默认10），系统会根据这两个参数计算分页偏移量。分类筛选参数categoryId为可选参数，当提供该参数时，查询结果只会包含指定分类的商品。关键词搜索参数keyword同样为可选参数，当提供该参数时，查询结果只会包含商品名称包含关键词的商品。

查询条件通过MyBatis Plus的LambdaQueryWrapper构建，首先添加状态条件确保只查询上架状态的商品，然后根据是否提供分类ID和关键词添加相应的筛选条件。查询结果按创建时间倒序排列，使得最新上架的商品排在前面。最后调用分页查询方法返回分页结果，包括当前页数据、总记录数、总页数等信息。

商品详情接口通过detail方法实现，接收商品ID作为路径参数。查询时首先尝试获取指定ID的商品记录，如果商品不存在则返回错误信息。商品存在则返回完整的商品信息，包括名称、描述、价格、库存、图片等详细信息。

### 5.3.2 商品搜索实现

系统实现了ProductServiceImpl类，提供商品搜索和分类查询功能。搜索功能支持对商品名称和描述进行模糊匹配，能够根据用户输入的关键词查找相关商品。

搜索功能通过searchProducts方法实现，接收关键词和返回数量限制两个参数。查询条件使用MyBatis Plus的条件构造器构建，首先筛选上架状态的商品，然后使用and方法组合多个like条件，实现对商品名称和描述的模糊匹配。查询结果通过last方法添加数量限制，确保只返回指定数量的搜索结果，避免返回过多无用的数据。

分类查询功能通过getByCategory方法实现，接收分类ID作为参数。查询条件筛选指定分类且上架状态的商品，返回该分类下的所有商品列表。该功能用于商品分类浏览场景，用户选择某个分类后可以查看该分类下的所有商品。

搜索和分类查询功能为智能助手模块的RAG检索提供了基础支持，智能助手可以根据用户的问题提取关键词，调用这些搜索功能查找相关商品，为后续的商品推荐提供数据支持。

## 5.4 购物车模块实现

### 5.4.1 添加购物车

系统实现了CartController类，处理购物车相关的HTTP请求。控制器提供了添加商品到购物车和获取购物车列表两个核心接口。

添加购物车接口通过add方法实现，接收包含商品ID和数量的请求体参数。方法首先从请求属性中获取当前登录用户的ID，该用户ID由JWT拦截器在请求处理前存入。然后调用购物车服务的addToCart方法处理业务逻辑，将用户ID、商品ID和数量传递给服务层。

获取购物车列表接口通过list方法实现，从请求属性中获取用户ID后调用购物车服务的getCartList方法获取该用户的购物车商品列表。返回的数据包含每件商品的详细信息，如商品图片、名称、单价、购买数量和小计金额等，方便前端展示购物车内容。

### 5.4.2 购物车服务实现

系统实现了CartServiceImpl类，处理购物车的业务逻辑。该类继承自ServiceImpl，拥有基本的数据库操作能力，并实现了CartService接口定义的方法。

添加商品到购物车的功能通过addToCart方法实现，该方法使用@Transactional注解标记为事务方法，确保操作的数据一致性。添加流程首先检查商品是否存在且处于上架状态，如果商品不存在或已下架则返回错误信息。然后检查库存是否充足，如果购买数量超过库存则返回错误信息。

接着检查该商品是否已在用户购物车中，如果存在则更新数量（累加新的购买数量），更新时再次检查累加后的数量是否超过库存。更新操作会修改现有购物车记录的quantity字段。如果不存在则创建新的购物车记录，保存用户ID、商品ID和数量等信息。

购物车服务的getCartList方法用于获取用户的购物车列表，该方法调用Mapper的自定义查询方法，关联查询购物车表和商品表，返回购物车商品视图对象列表。视图对象包含购物车ID、商品信息、单价、数量和小计金额等字段，方便前端直接展示。

购物车模块的实现确保了用户可以方便地管理购物车商品，支持修改购买数量和删除商品等操作，为用户提供了流畅的购物体验。

## 5.5 订单模块实现

### 5.5.1 创建订单

系统实现了OrderController类，处理订单相关的HTTP请求。控制器提供了创建订单和支付订单两个核心接口。

创建订单接口通过create方法实现，接收包含收货地址ID和购物车ID列表的请求体参数。方法从请求属性中获取当前登录用户的ID，然后调用订单服务的createOrder方法处理订单创建的业务逻辑。

支付订单接口通过pay方法实现，接收订单ID作为路径参数。该接口用于模拟订单支付流程，在实际系统中可以对接第三方支付平台实现真实的支付功能。支付成功后会将订单状态更新为已支付，并记录支付时间等信息。

### 5.5.2 订单服务实现

系统实现了OrderServiceImpl类，处理订单创建的完整业务流程。该类使用@Transactional注解标记事务，确保订单创建过程中的多个数据库操作要么全部成功，要么全部回滚，保持数据一致性。

订单创建流程包含以下步骤：

第一步，查询购物车商品。根据传入的购物车ID列表查询对应的购物车记录，如果购物车为空则返回错误信息。

第二步，验证库存并计算总金额。遍历购物车中的每件商品，检查库存是否充足。如果库存不足则返回错误信息，并指明是哪种商品库存不足。库存充足则计算该商品的金额（单价乘以数量），累加到总金额中，同时创建订单项对象记录商品信息。

第三步，创建订单记录。生成唯一的订单号（格式为"ORD"加上时间戳和随机数），设置订单的用户ID、总金额、收货地址ID和订单状态（初始为待支付）等信息，保存订单记录到数据库。

第四步，创建订单项记录。遍历之前创建的订单项对象列表，为每个订单项设置所属订单的ID，然后插入到数据库。订单项记录了每个商品的名称、单价和数量等信息，用于后续的订单详情展示。

第五步，扣减库存。遍历购物车商品，调用商品服务的库存扣减方法，减少相应商品的库存数量。库存扣减是订单创建的关键步骤，必须确保在事务中完成，避免超卖问题。

第六步，清空购物车。删除用户提交的购物车记录，完成整个订单创建流程。

该实现确保了订单创建的完整性和数据一致性，每个步骤都有相应的错误处理，任何一步失败都会触发事务回滚，保证不会出现库存扣减但订单未创建等异常情况。

## 5.6 智能助手模块实现

### 5.6.1 RAG检索服务

系统实现了RAGService接口和SimpleRAGServiceImpl实现类，提供检索增强生成（Retrieval-Augmented Generation）能力。RAG技术通过先检索相关文档再生成答案的方式，提高了LLM回答的准确性和相关性。

RAGService接口定义了检索相关商品和格式化商品信息两个方法。searchRelevantProducts方法接收用户查询和返回数量参数，提取用户查询中的关键词后搜索相关商品。formatProductsAsContext方法将商品列表格式化为文本上下文，作为LLM生成回复时的参考信息。

SimpleRAGServiceImpl实现了上述接口，具体实现采用基于关键词的检索策略。关键词提取功能通过extractKeywords方法实现，该方法首先定义停用词列表（如"我"、"想"、"要"、"买"等常见无意义词汇），然后对用户查询进行分词处理，过滤掉长度为1的字符和停用词列表中的词汇，保留有意义的关键词。

商品搜索功能构建复杂的查询条件，筛选上架状态的商品，并使用or条件组合多个关键词的like查询，实现对商品名称和描述的匹配。查询结果限制数量为指定的topK参数值，避免返回过多无关结果。

上下文格式化功能将搜索到的商品格式化为易于阅读的文本，每件商品包含序号、名称、价格和描述（截取前50个字符）。格式化后的文本作为用户消息的补充信息发送给LLM，使LLM能够基于真实的商品数据进行回答，提高回复的准确性和有用性。

### 5.6.2 LLM服务接口

系统定义了LLMService接口，提供与大语言模型交互的统一抽象。该接口采用策略模式设计，便于切换不同的LLM服务提供商。

LLMService接口定义了chat和chatStream两个方法。chat方法用于普通对话，接收消息列表并返回完整的回复字符串，适用于短文本生成场景。chatStream方法用于流式对话，接收消息列表和回调接口，边生成边返回回复内容，适用于长文本生成和实时交互场景。

流式回调接口StreamCallback是@FunctionalInterface类型的函数式接口，定义了onToken方法接收LLM返回的每个Token。这种设计使得LLM返回的内容可以即时处理和展示，无需等待完整响应生成完毕，显著提升了用户交互体验。

### 5.6.3 通义千问服务实现

系统实现了QwenLLMServiceImpl类，调用通义千问API实现LLM服务。该类使用@ConditionalOnProperty注解标记，仅当配置文件中llm.provider配置项值为qwen时才会被Spring容器加载，实现LLM服务提供商的灵活切换。

API调用功能通过chatStream方法实现，使用Java标准库的HttpClient发送HTTP请求。请求构建包括设置API地址、Authorization头（Bearer令牌认证）、Content-Type头和X-DashScope-SSE头（启用SSE流式输出），请求体采用JSON格式，包含模型名称、消息列表和输出参数等配置项。

流式响应处理通过HttpResponse.BodyHandlers.ofLines方法获取响应体的行迭代器，逐行解析SSE格式的数据。每行数据以"data:"开头，后面跟着JSON格式的响应内容。解析出Token后通过回调接口的onToken方法传递给调用方，调用方通常会将Token追加到响应内容中实现实时显示效果。

请求体构建功能通过buildRequestBody方法实现，将消息列表转换为通义千问API要求的JSON格式。消息类型包括system（系统消息，定义助手角色和行为）、user（用户消息）和assistant（助手消息，用于对话历史）。模型名称指定为qwen-turbo，该模型具有较好的性价比和响应速度，适合对话场景使用。

### 5.6.4 智能助手控制器

系统实现了AssistantController类，处理智能助手相关的HTTP请求。控制器提供了流式对话和获取会话列表两个核心接口。

流式对话接口通过chatStream方法实现，使用SSE（Server-Sent Events）技术实现服务器向客户端的持续推送。该接口创建SseEmitter对象作为SSE连接的核心，指定超时时间为60秒（60000毫秒），然后异步调用助手服务处理对话请求。

异步处理使用CompletableFuture的runAsync方法，在后台线程中执行耗时的对话处理逻辑。处理完成后通过SseEmitter发送完成信号，或在发生异常时发送错误信号。这种设计避免了阻塞HTTP请求线程，提高了服务器的并发处理能力。

获取会话列表接口通过getConversations方法实现，从请求属性获取用户ID后调用助手服务获取该用户的所有会话记录。会话记录包括会话ID、标题、创建时间和最后更新时间等信息，前端用于展示会话列表供用户选择。

### 5.6.5 智能助手服务实现

系统实现了AssistantServiceImpl类，处理智能助手的核心业务逻辑，是整个智能助手模块的核心组件。

对话处理功能通过handleStreamChat方法实现，包含完整的对话处理流程。

第一步，保存用户消息。将用户发送的消息内容保存到会话消息表中，记录消息角色为USER。这保证了对话历史的完整性，LLM可以基于上下文生成连贯的回复。

第二步，RAG检索相关商品。调用RAG服务的searchRelevantProducts方法，传入用户消息作为查询，获取最相关的5件商品。然后调用formatProductsAsContext方法将商品信息格式化为上下文文本。

第三步，获取历史消息。调用会话服务的getRecentMessages方法，获取当前会话最近10条消息记录，用于构建完整的对话上下文。

第四步，构建消息列表。创建一个包含系统消息、历史消息和当前用户消息的消息列表。系统消息定义了助手的角色定位，要求助手根据用户需求和商品信息给出专业的购物建议。

第五步，流式调用LLM。调用LLM服务的chatStream方法，传入消息列表和Token回调函数。回调函数负责将每个Token发送给客户端，并累加到完整响应字符串中。发送时使用SseEmitter.event()方法构建SSE事件，事件名称为"message"，数据为包含Token的JSON对象。

第六步，发送推荐商品。如果RAG检索到了相关商品，会将这些商品作为推荐结果发送给客户端。发送时使用事件名称为"products"的SSE事件，数据为商品列表的JSON数组。前端收到后会展示商品推荐卡片，方便用户查看和选择推荐商品。

第七步，保存助手回复。将LLM生成的完整回复保存到会话消息表中，记录消息角色为ASSISTANT，完成对话历史的记录。

第八步，发送完成信号。向客户端发送事件名称为"done"的SSE事件，通知客户端对话已完成，然后调用emitter.complete()关闭SSE连接。如果处理过程中发生异常，调用emitter.completeWithError(e)通知客户端连接异常关闭。

该实现确保了智能助手能够提供准确、相关、实时的购物建议，通过RAG技术结合真实的商品数据进行回复，通过SSE技术实现流式输出提升用户体验，通过消息历史管理实现多轮对话能力。

## 5.7 前端实现

### 5.7.1 Axios 请求封装（request.ts）

系统在前端通过 `src/api/request.ts` 基于 Axios 库创建了名为 `service` 的默认实例，作为全站 REST 调用的唯一出口。实例创建时配置了 `baseURL: '/api'` 与 `timeout: 30000`：前者与 Vite 开发代理配合，将浏览器请求统一转发到后端；后者避免弱网或服务阻塞时前端无限等待。

请求拦截器 `service.interceptors.request.use` 在每次发出请求前执行：从 `localStorage` 读取 `token`，若存在则写入请求头 `Authorization`，格式为 `Bearer` 加令牌内容，与后端 `JwtInterceptor` 的解析约定一致；同时写入 `userId` 请求头作为演示环境下的辅助标识（生产环境应以令牌解析结果为准）。响应拦截器 `service.interceptors.response.use` 在收到响应后统一判断业务码：若 `response.data.code === 200` 则直接返回 `res` 供页面使用；否则弹出 `ElMessage` 并 `Promise.reject`。错误分支中若 HTTP 状态为 401，则清除本地 `token` 与 `userId` 并跳转登录页，实现与会话失效配套的前端清理逻辑。

各业务模块通过 `import request from './request'` 引用该实例，例如 `product.ts`、`cart.ts`、`order.ts`、`assistant.ts` 等，从而保证认证头、超时与错误提示策略在全站一致。

### 5.7.2 助手 API 与流式客户端（assistant.ts）

系统在 `src/api/assistant.ts` 中声明了 `ChatRequest`、`ChatResponse`、`Conversation`、`AssistantSettings`、`AssistantTemplate` 等 TypeScript 接口，用于约束请求体与列表数据的字段形状。

同步对话由 `chat` 函数实现，向 `POST /assistant/chat` 提交 `ChatRequest`（含可选 `sessionId` 与 `message`），适用于非流式的一次性问答场景。流式对话由 `chatStreamPost` 异步函数实现：使用 `fetch` 以 `POST` 方式访问 `/api/assistant/chat/stream`，请求头携带 `Content-Type`、`Authorization` 与 `userId`，请求体为 JSON 序列化后的 `ChatRequest`；通过 `response.body.getReader()` 与 `TextDecoder` 分块读取响应流，在本地用 `buffer` 累积并按行拆分。对以 `data:` 开头的行，去掉前缀后若等于 `[DONE]` 则结束并调用 `onDone`；否则尝试 `JSON.parse`：若对象含 `products` 字段则更新本地 `relatedProducts` 引用，若含 `chunk` 字段则调用 `onMessage(chunk)` 将增量文本交给界面；解析失败时退化为整段字符串交给 `onMessage`，以兼容非 JSON 的纯文本推送。文件中还保留了基于 `EventSource` 的 `chatStream` 示例实现，注释中说明了 GET 式 SSE 的局限，与当前主路径采用的 `POST + fetch` 流式方案形成对照。

会话管理方面，`getConversations` 调用 `GET /assistant/conversations` 分页拉取会话列表；`getMessages` 调用 `GET /assistant/conversation/{sessionId}/messages` 拉取单会话历史；`deleteConversation` 调用 `DELETE /assistant/conversation/{sessionId}` 删除会话。管理端模板与设置则分别对应 `getAdminAssistantSettings`、`updateAdminAssistantSettings`、`getAdminAssistantTemplates`、`createAdminAssistantTemplate`、`updateAdminAssistantTemplate`、`deleteAdminAssistantTemplate` 等方法，路径前缀为 `/admin/assistant/...`。

### 5.7.3 智能助手页面与对话子组件

用户侧助手主视图由 `Assistant.vue` 实现。组件在 `onMounted` 钩子中调用 `loadConversations`，内部通过 `getConversations` 获取 `res.data.list` 填充左侧 `ConversationList`；若当前未选中会话且列表非空，则默认选中第一条并设置 `currentSessionId`。`watch(currentSessionId)` 在会话切换时触发 `loadMessages`：该函数调用 `getMessages(sessionId)`，将返回消息中的数值型 `role` 映射为 `'user' | 'assistant'` 字符串后写入 `messages`，供右侧 `ChatWindow` 渲染。

`ConversationList` 接收 `conversations`、`currentSessionId` 属性，向外派发 `select`、`new`、`delete` 事件；主组件在对应处理函数中更新当前会话、重新拉取列表或清空消息数组。发送完成后的刷新策略由 `handleSendMessage` 与 `ChatWindow` 协作：`ChatWindow` 内部在流式结束后可通知父组件，父组件在存在 `currentSessionId` 时再次调用 `loadMessages` 以保证与服务端消息表一致。

`ChatWindow.vue` 在发送逻辑中调用 `chatStreamPost`：构造 `ChatRequest` 后传入消息增量回调、完成回调与错误回调；在回调中更新本地消息列表中助手气泡的文本，并在收到 `relatedProducts` 时绑定到推荐商品展示区域。由此形成“页面状态管理在 `Assistant.vue`、流式协议解析在 `assistant.ts`、发送与气泡更新在 `ChatWindow.vue`”的分层结构。

## 5.8 系统界面展示

### 5.8.1 主要界面说明

**（1）商城首页**

商城首页承担入口与导流作用，一般包含顶栏、内容区与底部或侧边的辅助信息。顶栏通常放置系统标识、全局搜索或快捷入口、购物车与个人中心等链接，使用户在任意深度页面仍能快速回到核心功能。内容区常展示推荐商品、新品或活动位，以图文卡片形式吸引点击；若首页与商品列表共用数据源，则同样依赖后端的在售商品过滤与分页策略，保证展示与列表页规则一致。首页与列表页是否提供“按销量、价格排序”等能力，取决于具体页面实现；本系统在商品列表页中提供了搜索与分页组合，首页更侧重导航与精选展示而非完整检索。

**（2）商品详情页**

详情页围绕单件商品组织信息：主图与文字说明帮助用户建立直观印象，价格与库存提示购买可行性，购买数量选择与加入购物车等操作把浏览转化为加购行为。部分实现还会在详情页提供用户评价与收藏功能，评价有助于建立信任，收藏便于用户稍后对比。若业务上未接入“一键下单”的独立链路，则用户往往在确认购物车与地址后再统一结算，详情页以加购为主、跳转购物车为辅，避免在详情页堆积过多下单步骤导致界面臃肿。

**（3）购物车页面**

购物车页以行表形式列出待结算商品，每行聚合图片、名称、单价、数量与小计。数量调整既可通过步进控件也可通过键盘输入，但上限不应超过实时库存。页头或行内提供选择与删除能力，页尾汇总已选商品金额并给出结算入口。结算前通常要求用户已维护收货地址；若地址缺失或失效，应在跳转或提交前给出明确提示，减少订单创建失败后的往返成本。

**（4）智能助手页面**

助手页在视觉上接近即时通讯应用：一侧是会话历史列表，另一侧是当前会话的消息流与输入区。消息流中区分手写用户发言与助手回复，助手侧可挂载推荐商品块，支持从卡片进入详情以完成加购。输入区除文本发送外，可根据产品规划扩展快捷问题或清空会话等操作。长时间无响应时应有超时或失败提示，避免用户误以为系统卡死。

### 5.8.2 日志与异常处理

系统实现过程中，日志与异常处理是保障运行稳定性的关键环节。后端使用Slf4j作为日志框架，这是Java生态中最常用的日志门面系统，提供了统一的日志API，支持多种日志实现（如Logback、Log4j2）。

后端日志记录覆盖关键业务流程的各个环节。用户登录时记录用户ID和登录结果，便于追踪用户行为和排查登录异常。订单创建时记录订单号、用户ID和订单金额，便于订单问题排查和财务对账。LLM调用时记录请求内容、响应状态和耗时，便于性能监控和问题诊断。当LLM调用失败时，会记录详细的异常堆栈信息，便于定位问题原因。

日志级别根据情况选择合适的级别：Info级别记录正常的业务流程，如接口调用、业务处理完成等；Warn级别记录可能存在问题但不影响功能的情况，如库存不足建议补货；Error级别记录系统异常和错误，如数据库连接失败、API调用超时等。

前端使用Element Plus提供的Message组件实现统一的错误提示。请求失败时显示错误消息，如"网络错误，请检查网络连接"。认证失败时显示登录过期提示，并自动跳转到登录页面。业务错误时显示后端返回的错误信息，如"商品库存不足"。

后端实现全局异常处理器，使用@RestControllerAdvice注解标记。该处理器统一捕获业务异常（如用户名已存在、商品不存在）、参数校验异常（如必填参数缺失、参数格式错误）和系统异常（如空指针异常、类型转换异常），将异常信息封装为规范化的JSON响应返回给前端。响应包含错误码和错误消息，便于前端进行针对性处理。

对于智能助手模块，还额外处理了LLM服务特有的异常情况。API超时异常捕获后返回友好提示"服务响应超时，请稍后重试"。返回格式异常捕获后记录错误日志并返回"服务数据异常"提示。限流异常捕获后返回"服务繁忙，请稍后重试"提示。

### 5.8.3 异常处理与日志设计

本系统通过结构化日志记录关键业务事件，确保异常发生时可以快速定位问题根源。日志设计遵循以下原则：

日志内容包含足够的上下文信息，如用户ID、订单ID、商品ID等，便于关联查询相关数据。日志时间精确到毫秒，便于分析事件发生的先后顺序和性能问题。日志格式采用结构化格式（如JSON），便于日志收集和检索系统处理。

后端日志可以与日志聚合平台对接，实现集中式的日志管理和分析。常用的方案包括ELK（Elasticsearch、Logstash、Kibana）技术栈或云服务商提供的日志服务。通过日志聚合平台，开发人员可以快速检索、筛选和分析海量日志数据，大大提高了问题定位效率。

日志记录同时包含正常流程和异常流程的记录。正常流程记录有助于了解系统的运行状况和用户行为模式，异常流程记录有助于排查问题和优化系统。

前端在请求失败时统一提示用户，提示内容根据错误类型有所区别。网络错误提示"网络连接失败，请检查网络设置"。认证失败提示"登录已过期，请重新登录"并自动跳转登录页。服务器错误提示"服务器异常，请稍后重试"。限流错误提示"操作过于频繁，请稍后再试"。

对于智能助手会话，系统特别记录生成失败、超时和重试行为。这些日志数据对于分析模型调用稳定性、系统表现和用户体验至关重要。开发人员可以通过分析这些日志识别LLM服务的常见问题，优化调用策略，提高服务质量。

### 5.8.4 工程实践要点

在实际实现中，系统遵循了前后端分离的设计原则，保持了后端服务与前端页面的功能边界清晰。这种设计提高了系统的可维护性和可扩展性，使得前后端可以独立开发和部署。

后端主要负责数据处理、业务校验和外部服务集成。数据处理包括数据库CRUD操作、数据转换和聚合计算等。业务校验包括参数合法性检查、权限验证和业务规则验证等。外部服务集成包括LLM服务调用、第三方支付对接等。这种职责划分使得后端专注于业务逻辑和数据处理，提供了稳定可靠的API服务。

前端主要负责界面展示、用户输入和请求流转。界面展示包括组件渲染、动画效果和响应式布局等。用户输入包括表单处理、事件响应和状态管理等。请求流转包括API调用、数据缓存和错误处理等。这种职责划分使得前端专注于用户体验和交互逻辑，提供了良好的用户界面。

系统引入了自动化测试、代码审查和持续集成流程，从多个层面保障代码质量和系统稳定性。

自动化测试包括单元测试和集成测试两个层次。单元测试针对单个类或方法的逻辑进行验证，确保每个代码单元的行为符合预期。集成测试针对多个组件的协作进行验证，确保系统各部分能够正确交互。测试覆盖了核心业务逻辑，包括用户认证、商品查询、订单创建和智能助手对话等关键功能。

代码审查通过Pull Request流程实现，团队成员相互审查彼此的代码变更。代码审查可以发现潜在的bug、优化代码结构、分享技术经验，并确保代码符合团队规范。审查重点包括业务逻辑正确性、异常处理完备性、安全性检查和性能考虑等。

持续集成通过自动化流水线实现，每次代码提交会自动触发构建和测试流程。流水线包括代码编译、依赖安装、测试执行、代码检查和构建产物生成等步骤。如果某个步骤失败，团队成员会收到通知并及时修复问题。这种机制确保了代码质量的持续监控和问题早发现、早解决。

## 5.9 用户端模块实现

本节在用户可见功能与源码实现之间建立对应关系：依次说明商品列表与详情页、订单列表与弹窗详情、购物车页与结算、智能助手页如何调用前端 API 模块，以及这些调用如何落到后端的控制器与服务类上。写法与 5.6.1 节 RAG 部分一致，既交代“做了什么”，也点名“由谁实现、关键方法是什么”。

### 5.9.1 用户端商品模块

系统通过 `ProductList.vue` 视图组件实现用户端商品列表与站内搜索。脚本中使用 `ref` 维护 `products`（当前页商品数组）、`keyword`（搜索词）、`page` 与 `size`（分页参数）。`load` 异步方法根据 `keyword` 是否为空分支调用 `src/api/product.ts` 中的 `searchProducts` 或 `getProductList`：前者向后端发起带关键词的分页检索，后者发起普通分页列表请求；二者返回的数据均写入 `products`，供模板中的 `el-row`/`el-col` 与 `el-card` 循环渲染。分页由 `el-pagination` 双向绑定 `page`、`size`，在 `size-change` 与 `current-change` 事件中再次调用 `load`，从而形成“改页码或每页条数即重新拉数”的闭环。

`handleSearch` 方法在点击搜索或键盘回车时将 `page` 置为 1 并调用 `load`，避免带着旧页码去请求新的关键词结果集。`goDetail` 使用 Vue Router 跳转至 `/products/{id}` 进入详情。`handleAddCart` 调用同目录下封装好的 `addCart` 方法（定义于 `cart.ts`），请求体为 `{ productId, quantity: 1 }`，成功后以 `ElMessage.success` 提示用户；失败路径展示后端或拦截器返回的错误信息。模板中商品主图使用 `el-image`，通过 `error` 插槽在地址无效时展示“暂无图片”占位，与弱网或资源缺失场景兼容；卡片整体绑定点击跳转详情，加购按钮使用 `@click.stop` 阻止冒泡，避免用户意图为加购时误进入详情。

商品详情由 `ProductDetail.vue` 实现。`onMounted` 中根据路由参数 `id` 调用 `getProductById` 拉取单条 `Product` 实体，填充主图、标题、价格、库存与描述。购买数量由 `qty` 与 `el-input-number` 绑定，最大值为当前 `stock`。`handleAddCart` 将 `{ productId, quantity: qty.value }` 提交给 `addCart`。页面还集成评价与收藏：`createReview`、`getProductReviews` 等来自 `review.ts`，`addFavorite`、`removeFavorite`、`checkFavorite` 来自 `favorite.ts`，用于发表评价、拉取列表与切换收藏状态，与商品主数据共同构成详情页的完整体验。

**（2）与后端商品服务的对应关系**

`product.ts` 中 `getProductList(page, size)` 封装对 `GET /products` 的访问，`searchProducts(keyword, page, size)` 封装对 `GET /products/search` 的访问，查询参数与 `ProductList.vue` 中的 `page`、`size`、`keyword` 一一对应。`getProductById(id)` 对应 `GET /products/{id}`，供详情页拉取单条记录。上述路径经 `request.ts` 统一加上 `/api` 前缀并由 Vite 代理转发至 Spring Boot。

用户端列表与搜索所依赖的后端能力对应 5.3 节中的 `ProductController` 与 `ProductServiceImpl`：控制器负责解析分页与关键词参数并返回统一 `Result` 包装；服务实现类内部通过 MyBatis Plus 的 `LambdaQueryWrapper` 构造条件，例如限定 `status` 为上架、对 `name`/`description` 做 `like` 模糊匹配等。前端 `export interface Product` 与后端实体 JSON 字段对齐，减少手工拼装字段的错误。首页若展示热门、新品，可复用同文件中的 `getHotProducts`、`getNewProducts`，分别对应 `GET /products/hot` 与 `GET /products/new`，数据流与列表页一致。

**（3）弱网、空结果与图片降级**

`load` 方法在 `catch` 分支调用 `ElMessage.error` 提示“加载商品失败”或后端返回信息，与“关键词命中为空”区分：后者应走 `el-empty` 展示“暂无商品”，而不是当作异常。`el-image` 的 `error` 插槽在图片 404 或跨域失败时展示占位文案，避免整卡空白。搜索将 `page` 重置为 1，可防止用户停留在高页码而关键词结果实际不足一页时出现空数据的困惑。

### 5.9.2 用户端订单模块

系统通过 `OrderList.vue` 实现“我的订单”页面。组件使用 `el-tabs` 绑定 `activeStatus`，各 `el-tab-pane` 的 `name` 与订单状态数值对应：`undefined` 表示全部，0～4 分别表示待支付、已支付、已发货、已完成、已取消。`handleStatusChange` 在切换标签时调用 `loadOrderList`，从 `src/api/order.ts` 中的 `getOrderList` 拉取当前用户订单列表（可按 `activeStatus` 传状态筛选参数）。每个订单渲染为 `el-card`：头部展示 `orderNo`、`createTime` 与 `el-tag` 状态；中部 `v-for` 遍历 `order.items` 展示行项目图片、名称、数量、单价与小计；底部汇总件数与 `totalAmount`，并根据 `order.status` 条件渲染“立即支付”“取消订单”“查看详情”等按钮。

`viewOrderDetail` 打开 `el-dialog`，内部通过 `getOrderDetail(orderId)` 拉取完整 `OrderDTO`，用 `el-descriptions` 展示订单号、状态、金额、地址及各 `OrderItem` 明细。`handlePay` 调用 `payOrder(orderId)` 走模拟支付：对应后端 `OrderController` 的支付接口，将状态从待支付更新为已支付并记录支付时间；成功后关闭弹窗并调用 `loadOrderList` 刷新列表。`handleCancel` 调用 `cancelOrder(orderId)`，仅允许在业务规则允许的状态下执行，成功后同样调用 `loadOrderList`。上述流程与 5.5 节中 `OrderServiceImpl` 的事务方法相呼应：用户端只负责触发与展示，库存回滚、状态迁移等仍由服务层保证。

**（2）与购物车、商品主数据的关系**

订单行展示的商品名称、单价、数量来自下单时写入的订单项快照，不应在详情页用当前 `Product` 列表价格覆盖。用户从 `Cart.vue` 结算成功后路由跳转到 `/orders`，因此列表接口的错误信息应能指导用户返回购物车或地址页；这与 `OrderServiceImpl.createOrder` 在校验库存、商品上架状态、地址合法性失败时抛出业务异常的设计一致。

**（3）体验与扩展说明**

状态标签颜色由 `orderStatusMap` 映射到 Element Plus 的 `type`，保证视觉与语义一致。已取消订单是否出现在默认“全部”标签下，取决于产品策略；若隐藏，则需在“全部”或单独标签中仍可查询，以免用户找不到历史记录。真实生产环境需在支付环节接入第三方支付与回调验签，本系统以模拟支付为教学简化，论文中应明确边界。

### 5.9.3 用户端购物车模块

系统通过 `Cart.vue` 实现购物车页。脚本中定义 `CartItemWithSelected` 类型，在 `initCartList` 中为每个 `CartItem` 附加布尔字段 `selected`，用于前端勾选而不修改数据库结构。`loadCartList` 调用 `getCartList`（定义于 `cart.ts`，对应后端 `CartController.getCartList` 的 `GET /cart/list`），将返回数组经 `initCartList` 赋给 `cartList`。

`computed` 属性 `selectedItems` 过滤出 `selected` 为真的行；`totalAmount` 对选中行累加 `subtotal`。`handleSelectAll` 在表头全选框变更时批量改写各行 `selected`；`handleItemSelect` 在单行勾选后根据是否全选更新 `selectAll`。`handleQuantityChange` 调用 `updateCartQuantity(item.id, { quantity: item.quantity })`，对应 `CartController.updateCartQuantity` 与 `CartServiceImpl.updateCartQuantity`：后端校验购物车项归属用户、库存上界后更新数量；前端在成功后用 `product.price * quantity` 回写 `subtotal` 并提示成功，失败则 `loadCartList` 重新拉取以恢复与服务端一致。`handleDelete` 与 `handleBatchDelete` 在 `ElMessageBox.confirm` 通过后循环或并行调用 `deleteCartItem`，对应 `DELETE /cart/{cartId}`，最后刷新列表。

`handleCheckout` 先判断 `selectedItems` 非空，再调用 `getDefaultAddress`（`address.ts`）获取默认地址；若无地址则弹框引导跳转 `AddressList` 路由。若有默认地址，则收集选中行的 `id` 组成 `cartItemIds`，调用 `createOrder({ cartItemIds, addressId })`（`order.ts` 中对应 `POST /order/create`），与 5.5 节 `OrderServiceImpl.createOrder` 使用同一请求体模型。创建成功后提示并 `router.push('/orders')`。该链路把前端的“勾选 + 默认地址”与后端的“按购物车项建单、扣库存、删购物车记录”连接起来。

**（2）与 CartServiceImpl 的对应关系**

后端 `CartServiceImpl.addCart` 使用 `@Transactional` 标注：先 `productMapper.selectById` 校验商品存在且 `status==1`，再比较库存；若当前用户已存在同一 `productId` 的购物车行，则累加数量并再次校验库存上限，否则插入新 `Cart` 记录。`getCartList` 按 `userId` 查询购物车表，按创建时间倒序，对每个 `Cart` 再查 `Product` 填充到 `CartItemDTO`，并用 `price.multiply(BigDecimal.valueOf(quantity))` 计算 `subtotal`。`updateCartQuantity`、`deleteCartItem`、`clearCart` 分别对应控制器的 `PUT /cart/{id}`、`DELETE /cart/{id}`、`DELETE /cart/clear`，内部均校验记录归属，防止越权操作其它用户购物车。其中 `clearCart` 已在 `cart.ts` 中封装为 `clearCart()`，当前 `Cart.vue` 界面以单行删除与批量删除为主，未放置“一键清空”按钮；若产品需要，可直接复用该接口而无需改动服务层。

### 5.9.4 用户端智能助手模块

用户端助手由 `Assistant.vue` 组合子组件 `ConversationList.vue` 与 `ChatWindow.vue` 构成。`loadConversations` 调用 `getConversations`，读取 `res.data.list` 填充 `conversations`，并在无当前会话时默认选中第一条。`loadMessages` 在选中会话后调用 `getMessages(sessionId)`，将消息中的数值型 `role` 映射为字符串 `'user' | 'assistant'` 后写入 `messages`。`handleDeleteConversation` 调用 `deleteConversation` 删除服务端会话并刷新列表。

流式对话的发送与 `chatStreamPost` 的调用位于 `ChatWindow.vue`：组件导入 `chatStreamPost` 与类型 `ChatRequest`，在发送时构造 `{ sessionId, message }` 请求体，注册 `onMessage` 以追加助手文本、`onDone` 以附带推荐商品列表结束加载、`onError` 以提示失败。该函数内部按行解析 `data:` SSE 片段，与 5.7.2 节描述一致。`Assistant.vue` 中 `handleSendMessage` 在发送完成后若存在 `currentSessionId` 则再次 `loadMessages`，保证界面与数据库消息表同步。

路由层在 `router/index.ts` 将 `/assistant` 映射到 `Assistant.vue`，并设置 `requiresAuth: true`，与 `request.ts` 中附带令牌、`chatStreamPost` 中附带 `Authorization` 头共同保证：REST 与流式请求都指向当前登录用户，后端 `AssistantController` 将会话与消息绑定到 `RequestAttribute` 中的 `userId`，避免会话串扰。

## 5.10 管理端模块实现

管理端页面位于 `views/admin` 目录，通过 `AdminLayout` 与独立路由前缀 `/admin` 与用户端隔离。以下各小节分别对应 `ProductList.vue`、`AddProduct.vue`、`OrderList.vue`、`OrderAnalysis.vue`、`AdminAssistant.vue` 等组件，并写出其调用的 API 方法名与后端职责，便于与 5.3～5.6 节对照阅读。

### 5.10.1 管理端商品模块

系统通过 `views/admin/ProductList.vue` 实现后台商品列表。脚本中 `searchForm` 为 `reactive` 对象，字段包含 `keyword`、`category`（分类 ID）、`status`（上下架）。`fetchProductList` 调用 `getAdminProductList`（`product.ts`），传入 `page`、`size`、`keyword`、`categoryId`、`status`，对应后端管理端分页接口；返回的 `list` 经 `map` 附加 `categoryName`（由本地 `getCategoryName` 根据 `categoryId` 映射手机、电脑等中文名，属演示数据简化）。`pagination` 对象维护 `currentPage`、`pageSize`、`total`，与表格底部分页器双向绑定。`handleStatusChange` 在用户拨动 `el-switch` 时调用 `updateProductStatus(row.id, row.status)`；若请求失败，在 `catch` 中将 `row.status` 反转回旧值，避免 UI 与数据库不一致。`handleDelete` 调用 `deleteProductApi(row.id)`（即 `deleteProduct`），并在 `deleteLoading` 防抖期间禁止重复点击。`handleEdit` 使用 `router.push('/admin/products/add?id=' + row.id)` 进入编辑态；页眉“添加商品”按钮跳转无参的同一表单页用于新增。

`AddProduct.vue`（未在本段逐行展开）在提交时根据是否存在 `id` 调用 `addProduct` 或 `updateProduct`，图片可先通过 `uploadProductImage` 上传再写入 `imageUrl` 字段；可选地调用 `generateProductContent` 辅助生成文案。用户端 `ProductList.vue` 只展示上架商品，依赖后端用户列表接口过滤 `status`；管理端列表展示全量状态，二者通过同一套商品主数据表实现联动。

### 5.10.2 管理端订单模块

系统通过 `views/admin/OrderList.vue` 实现全站订单检索。`searchForm` 包含 `orderNo`、`userName`、`status`；`fetchOrderList` 调用 `getAdminOrderList`（`order.ts`），参数携带分页与筛选条件，对应 `GET /admin/orders`。表格列展示订单号、用户名、格式化金额、状态标签、各时间字段；`handleView` 打开弹窗并调用 `getAdminOrderDetail` 拉取详情。`handleShip` 在状态为已支付时调用 `shipOrderByAdmin`；`handleCancel` 在待支付时调用 `cancelOrderByAdmin`，与用户在 `OrderList.vue` 中调用的 `payOrder`、`cancelOrder` 形成角色隔离：管理端接口应对管理员 JWT 再校验。

`OrderAnalysis.vue` 提供日期区间、`analysisType`（按日期/商品/用户）与年份选择等筛选控件，`handleAnalysis` 根据类型组装请求并填充 `stats` 与 `chartData`；当前图表区以简易柱状示意占位，注释中预留接入 ECharts 等库的位置，论文中应写明其为可扩展分析入口而非完整 BI。

**（5）高峰期列表的非功能注意点**

订单列表在促销期数据量陡增时，除分页外还可考虑导出异步化、关键列冻结、骨架屏等体验优化；本实现以基础表格为主，上述项可作为后续迭代写入论文展望。

### 5.10.3 管理端购物车模块

后端购物车入口集中在 `CartController`：`POST /cart/add`、`GET /cart/list`、`PUT /cart/{cartId}`、`DELETE /cart/{cartId}`、`DELETE /cart/clear` 均通过 `@RequestAttribute("userId")` 绑定当前登录用户，未提供 `/admin/cart/**` 一类管理接口。因此管理端没有独立的购物车 CRUD 页面；运营分析若需购物车维度，应新增受角色保护的只读 API 或离线数仓任务，而不是复用用户购物车写接口。

排障时，`OrderServiceImpl.createOrder` 内调用的 `cartService.getCartItemsByIds` 与库存校验逻辑，已能解释大部分“结算失败”原因；若未来增加“按用户查看购物车快照”功能，必须在服务层记录审计日志并限制批量查询范围。

### 5.10.4 管理端智能助手模块

系统通过 `AdminAssistant.vue` 实现助手运营配置。`loadAssistantData` 使用 `Promise.all` 并行调用 `getAdminAssistantSettings` 与 `getAdminAssistantTemplates`（均定义于 `assistant.ts`，路径分别为 `GET /admin/assistant/settings` 与 `GET /admin/assistant/templates`），分别填充 `assistantSettings` 与 `templates` 表格。`saveSettings` 调用 `updateAdminAssistantSettings`，提交前校验 `name` 非空。模板新增/编辑在 `saveTemplate` 中分支：若 `currentTemplate.id` 存在则 `updateAdminAssistantTemplate`，否则 `createAdminAssistantTemplate`；`deleteTemplate` 调用 `deleteAdminAssistantTemplate`。

需要再次强调：通义千问模型名、温度、DashScope 密钥等仍主要由后端 `application.yml` 与 `QwenLLMServiceImpl` 管理；本页配置侧重助手名称、启用开关、`responseMode`、`timeout` 等业务层参数。用户端对话仍由 `AssistantServiceImpl.handleStreamChat` 驱动 RAG 与 LLM；管理端模板是否参与命中由后端策略决定，论文中应如实区分“已接入”和“仅前端表单预留”。

## 5.11 本章小结

本章在结构上延续了 5.1～5.6 节对后端类与方法的写法，在 5.7～5.10 节把同样的粒度延伸到前端：说明了 `request.ts` 拦截器行为、`assistant.ts` 中 `chatStreamPost` 的流式解析、`ProductList.vue`/`ProductDetail.vue`/`Cart.vue`/`OrderList.vue`/`Assistant.vue` 与 `ChatWindow.vue` 的职责划分，以及管理端 `ProductList.vue`、`OrderList.vue`、`OrderAnalysis.vue`、`AdminAssistant.vue` 所调用的 `getAdminProductList`、`getAdminOrderList`、`getAdminAssistantSettings` 等 API 与后端控制器的对应关系。购物车在后端由 `CartServiceImpl` 的事务方法保证一致性，在管理端则以“无独立页面、可扩展只读统计”为边界写清实现范围。

整体上，系统已形成从商品检索、购物车维护、订单创建与支付模拟、到 RAG 增强对话与 SSE 推送推荐的闭环；后续可在管理端购物车统计、助手会话审计、订单分析可视化深度等方面继续增强。本章对已实现部分给出类名与方法级描述，对未实现部分明确停留在扩展建议层面，避免与源码脱节。
