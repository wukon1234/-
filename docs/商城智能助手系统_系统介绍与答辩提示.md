## 一、项目概述

### 1.1 系统名称与定位

- **系统名称**：商城智能助手系统（`mall-backend`、`mall-frontend` 的 `pom.xml` / `package.json` 描述一致）。
- **系统定位**：**B/S、前后端分离** 的电商业务系统：用户端完成浏览、购物车、订单、地址、评价、收藏等；管理端完成商品/用户/订单与数据统计。**差异化核心** 是在商城真实数据之上实现 **对话式智能助手**，采用 **RAG（检索增强生成）+ 大语言模型** 编排，支持 **普通响应与 SSE 流式响应**、**多轮会话落库**、**管理端运营策略（停用 / 模板 / 智能）**，并与 **内容安全检测** 联动。

### 1.2 建设目标（可分条写入论文「研究目标」）

| 维度 | 目标 |
|------|------|
| 业务 | 提供可演示的完整网购闭环与管理闭环 |
| 智能 | 助手回答 **绑定本商城商品与当前用户订单事实**，控制幻觉；支持语义/关键词双路径检索 |
| 体验 | 流式打字效果、会话列表与历史、消息下挂 **可点击商品推荐卡片** |
| 治理 | 入站对话先过内容检测；助手可一键暂停或走固定模板 |
| 工程 | 分层清晰、接口化 LLM/RAG、可配置切换检索模式与向量库 |

### 1.3 工程结构

- **`mall-project/mall-backend`**：Spring Boot 单体应用，包根 `com.mall`，入口 `MallApplication`。
- **`mall-project/mall-frontend`**：Vue3 + Vite SPA，用户端布局 `MainLayout`，管理端 `AdminLayout`，助手页路由 `/assistant`。

## 二、总体架构

### 2.1 逻辑三层

| 层次 | 实现 | 职责 |
|------|------|------|
| 表现层 | Vue3 + Router + Pinia + Element Plus + Vite | 页面、路由守卫、助手 UI、HTTP/SSE 消费 |
| 应用层 | Spring Boot 2.7.18 | Controller → Service → Mapper；JWT；助手编排；RAG；LLM HTTP |
| 数据层 | MySQL + Druid + MyBatis-Plus；Redis；可选 Chroma/Milvus + Embedding | 业务持久化；可选语义向量 |

### 2.2 运行与网络

- 前端开发：`vite` 默认 **3000**，`/api` 代理到后端 **8087**（`mall-frontend/vite.config.ts`）。
- 后端：`server.port=8087`，`context-path=/api`，故浏览器经代理访问路径形如 `/api/assistant/chat`。
- 大模型：默认实现为 **通义千问** HTTP API（`QwenLLMServiceImpl`），模型名 **`qwen-turbo`**，支持 `stream: true` 流式增量解析。

### 2.3 智能助手在全局中的位置（答辩可画框图）

```text
[用户浏览器]
    │  JSON / SSE(fetch ReadableStream)
    ▼
[AssistantController] ──► [ContentCheckInterceptor]（助手 chat 入站）
    │
    ▼
[AssistantServiceImpl] ◄──► [ConversationMapper / ConversationMessageMapper]
    │                    ◄──► [AssistantSettingsMapper / AssistantTemplateMapper]
    │
    ├──► [RAGService / SimpleRAGServiceImpl]
    │         ├── ProductRAGDataSource（关键词打分）
    │         ├── OrderRAGDataSource（用户订单 + 意图触发）
    │         └── 可选：EmbeddingService + VectorStore（语义检索）
    │
    └──► [LLMService / QwenLLMServiceImpl]（非流式 / 流式）
```

## 四、用户端功能详细说明

用户端基于 `MainLayout.vue`：顶部 **粘性导航**（桌面横排菜单 + 移动端抽屉），入口包括：首页、商品、购物车、订单、地址、个人中心、收藏、智能助手。以下按 **页面 / 路由** 说明功能点及主要后端接口（路径均相对于 `context-path` 的 `/api`，前端经 Vite 代理为 `/api/...`）。

**全局鉴权**：除 `/login`、`/register` 外，业务页 `requiresAuth: true`，无 `localStorage.token` 跳转登录。请求头携带 `Authorization: Bearer <token>`（由 `src/api/request.ts` 统一封装）。

**订单状态约定**（用户端与管理端共用）：`0` 待支付、`1` 已支付、`2` 已发货、`3` 已完成、`4` 已取消。订单号格式为 **`ORD` + 时间戳 + 随机数**（`OrderServiceImpl.generateOrderNo`），与助手订单 RAG 正则一致。

## 五、管理端功能详细说明

管理端基于 `AdminLayout.vue`：顶栏 **ADMIN.OS** 标识、当前用户名下拉（个人中心占位链接、退出清除 token 并跳转 `/admin/login`）；左侧菜单：**仪表盘**、**商品管理**（列表 / 添加）、**订单管理**（列表 / 分析）、**用户列表**、**智能助手管理**。路由前缀 `/admin`，登录页 `/admin/login` 无侧栏。

### 6.1 产品定位与能力边界（答辩「需求与范围」页）

**助手扮演角色**：系统提示词中定义为 **「商城智能购物助手」**，仅回答与本商城购物相关的问题（商品咨询、选品对比、库存与价格、下单与支付流程、配送与售后、**订单与物流查询** 等）。若用户问题与商城无关，要求模型礼貌拒绝并说明只能回答本商城相关问题。

**能力边界（与实现对齐）**：

1. **商品信息**：来自 RAG 检索结果 + 模型常识性购物引导；检索无结果时仍允许基于「通用电商流程」说明，但不得编造具体 SKU。
2. **订单与物流**：**严格依据** RAG 注入的「订单系统检索结果」中的字段回答；提示词明确要求 **不得编造订单号或第三方快递轨迹**。订单侧的「物流」在实现上为 **基于订单状态推导的履约说明**（`OrderRAGDataSource.logisticsSummary`），**未对接真实快递公司轨迹 API**——答辩时应如实说明为「业务级物流阶段说明」而非「查快递单号」。
3. **多轮对话**：最近若干条历史消息会作为 LLM `messages` 上下文传入；会话与消息 **持久化到 MySQL**。
4. **运营控制**：管理员可将助手 **整体停用**，或切换为 **模板模式**（关键词命中则不走大模型），用于演示、降级与成本控制。

### 6.4 单次对话后端编排流程（答辩「时序图」页）

以下以 `AssistantServiceImpl.chat` 为主流程（流式逻辑相同，仅在第 6 步改为 `llmService.chatStream` 且通过回调推送）。

1. **会话解析**：若请求带有效 `sessionId` 且库中存在对应 `Conversation`，则复用；否则 **新建会话**（新 `sessionId`、标题「新对话」、`userId` 来自控制器从 JWT 解析；若为空则代码中存在默认用户 ID 兜底——**生产环境应删除该兜底并强制登录**）。
2. **落库用户消息**：`conversation_message.role=1`，写入 `content`。
3. **管理端策略短路**（`resolveManagedReply`）  
   - 读取最新一条 `AssistantSettings`。若 `enabled=0`：直接返回固定话术「当前智能助手已暂停服务，请稍后再试。」，**不调 RAG/LLM**。  
   - 若 `responseMode=template`：遍历所有 `AssistantTemplate`，若用户 `message.trim()` **包含** 某模板 `keyword.trim()`（子串匹配），则返回该模板 `response`，**不调 RAG/LLM**。  
   - 若模板模式下 **未命中任何关键词**：返回 `null`，**自动回退** 到智能链路（兼顾「常见问题固定答」与「开放域仍可调模型」）。
4. **RAG 检索商品**：`ragService.searchProducts(message, 5)`，默认 Top **5** 件商品进入提示词与响应 `relatedProducts`。
5. **RAG 检索当前用户订单**：`ragService.searchUserOrders(userId, message, 5)`，仅在订单数据源判定需要检索时返回结构化列表（见 5.8）。
6. **构建系统提示词**：`buildPrompt(userMessage, products, orders, conversationId)`（见 5.10）。
7. **组装多轮历史**：`getHistoryMessages(conversationId, 10)`：按创建时间倒序取最近 **10** 条消息，反转为时间正序，映射为 OpenAI 风格 `role`：`user` / `assistant`。
8. **调用 LLM**：`llmService.chat(prompt, history)` 或流式 `chatStream`。
9. **落库助手消息**：`role=2`，`relatedProducts` 为本次 RAG 商品 ID 的 JSON 数组。
10. **返回**：`ChatResponse` 带 `sessionId`、回复正文、商品列表、`messageId`。

**流式路径附加行为**（`chatStream`）：在子线程中执行；模型流式回调收到的 chunk 经 **`streamBySemanticUnits`** 再切分后回调到 `SseEmitter`；全量回复落库后通过 `callback.onProducts` 把商品列表再推给前端；`AssistantController` 将 chunk 封装为 `SseEmitter.event().name("message").data(chunk)`，并设置防缓冲响应头。

### 6.5 RAG 总控：`SimpleRAGServiceImpl`

**职责**：注册所有 `RAGDataSource` Bean（Spring 注入 `List<RAGDataSource>`），维护 `Map<DataSource, RAGDataSource>`；对外提供 `searchProducts`、`searchUserOrders`、`search` / `searchMulti`、商品变更时向量 **upsert/delete** 等。

**商品检索 `searchProducts`** 决策链：

1. 若配置为 **向量模式且就绪**（`rag.vectorEnabled=true` 且 `rag.searchMode=vector` 且 `EmbeddingService`、`VectorStore` 非空）：先 **`vectorSearchProducts`**：对用户查询做 **embedding** → 向量库 **query** 得商品 ID 列表 → **按向量顺序** 用 `productMapper.selectBatchIds` 拉回实体，并 **过滤仅上架（status=1）**；若向量为空则 **回退关键词检索**。  
2. 否则走 **`ProductRAGDataSource` 关键词路径**。  
3. 若向量检索 **抛错**：记录 warn 并返回空列表，同样可触发关键词回退（在 `searchProducts` 外层逻辑中体现「先向量、空则关键词」）。

**商品向量同步**（`syncAllProductsToVectorStore`）：遍历所有上架商品，用 `buildProductText` 拼接 **名称+描述+规格+价格+库存** 作为文档文本；`embedBatch` 批量向量化；`vectorStore.upsert` 写入 id、向量、文档、元数据（含 `type=product`、`id`、`categoryId`、`price`、`stock`）。单商品更新走 `upsertProductToVectorStore`。

---

### 6.6 商品数据源：`ProductRAGDataSource`（关键词 / 打分检索）

**数据范围**：仅 `status=1`（上架）商品。支持可选 `filters`：`categoryId`、`minPrice`、`maxPrice`（当前助手主流程未从 UI 传入复杂 filters，以用户自然语言查询为主）。

**打分规则 `scoreProduct`（答辩「算法设计」可讲）**：

- 将用户查询转小写，按 **空格、中文逗号、英文逗号** 拆成多个关键词。
- 每个关键词：若在 **商品名** 中出现 **+5**；在 **描述** 中 **+3**；在 **规格 JSON 文本** 中 **+2**。
- 若已有正分且存在价格：  
  - 查询含「便宜」「入门」「cheap」等：对低价商品 **额外加分**（简单反比函数）。  
  - 查询含「高端」「旗舰」「expensive」等：对高价商品 **额外加分**。  
- 得分为 0 的商品被过滤；按得分降序取 TopK。

**空查询语义**：`query` 为空或全空白时返回基础分 **1.0**，使「无关键词」场景仍能召回一批上架商品（便于扩展「随便看看」类话术）。

---

### 6.7 订单数据源：`OrderRAGDataSource`（隐私与意图触发）

**安全前提**：`filters` 中必须带 **`userId` 为 Number** 且 `>0`，否则 **直接返回空列表**，保证不跨用户泄露订单。

**是否检索订单 `shouldRetrieveOrders`**（仅当用户话术中命中以下之一才检索，避免每条对话都查库）：

- 正则匹配形如 **`ORD` 开头的订单号**（`\b(ORD\d+)\b`，大小写不敏感），或「订单号：xxx」类标签格式。  
- 或包含：「我的订单」「订单状态」「订单物流」「物流」「快递」「发货」「到哪了」「订单号」「查订单」「订单详情」（且非「如何/怎么下单」类纯流程咨询）等启发式关键词。  
- **显式排除**：「如何下单」「怎么下单」「下单流程」等 **纯流程教学问句** 不触发订单库检索，避免把「教程问题」误判为查单。

**检索策略**：

1. 若从用户话术中 **解析到订单号集合**：对每个单号在 **当前 userId** 下精确查 `order_no`；找到则 `toOrderMap`；找不到则插入 **`type=order_miss`** 的提示图，提示用户核对账号或单号。  
2. 若无明确单号但 **需要检索**：取该用户最近 `topK`（上限 50）条订单按创建时间倒序。

**订单结构化字段**（写入 prompt 的「订单系统检索结果」块）：订单号、金额、数值状态与 **中文状态文案**、创建/支付/发货/完成时间、**明细摘要**（商品名×数量拼接）、**履约说明 `logisticsSummary`**（按状态 0~4 分支生成，明确说明 **未对接第三方快递轨迹**）。

### 6.8 提示词工程：`buildPrompt` 设计要点（答辩「提示工程」页）

拼接顺序与约束（实现于 `AssistantServiceImpl.buildPrompt` / `appendOrderRagBlock`）：

1. **角色与拒答域**：声明为商城购物助手，仅处理商城相关问题，否则礼貌拒答。  
2. **订单证据块**（若有）：以标题 **「【订单系统检索结果】（当前登录用户，来自数据库）」** 引入；每条订单一行式罗列单号、金额、状态、各时间节点、明细、履约说明；`order_miss` 类型输出「未找到」类提示。  
3. **商品证据块**：列出最多 5 条检索商品的 **名称、简介、价格**；若无检索结果则说明「未检索到相关商品」，仍允许按通用规则引导。  
4. **用户当前问题**：原文追加。  
5. **回答规范**（硬约束，降低幻觉）：  
   - 简体中文、友好专业、分点分段。  
   - 推荐商品时必须 **引用列表中商品名并结合价格** 说理由。  
   - 下单/支付/配送/售后按 **常见电商流程** 分步骤。  
   - **订单状态/物流/详情必须严格依据检索块字段**；无数据且问个人订单时引导至「我的订单」或登录重试。  
   - 输出结构：**先「思路：」2~4 句，再「回答：」完整建议**。

该设计体现：**RAG 提供「事实锚点」+ 提示词提供「行为与格式约束」**，是论文中「降低幻觉」的理论与实现结合点。

### 6.9 大模型调用：`QwenLLMServiceImpl`

- **配置**：`llm.provider` 为 `qwen` 时生效；`llm.qwen.api-key`、`llm.qwen.base-url` 可配。  
- **非流式**：POST DashScope 兼容路径 `.../services/aigc/text-generation/generation`，`model=qwen-turbo`，`input.messages` 为历史 + 当前 user content（此处将整个 `buildPrompt` 结果作为 **一条 user message** 拼在 messages 末尾；历史为库中 user/assistant 对话）。解析 `output.text`。  
- **流式**：请求体设 `"stream": true`，逐行读取响应，`data:` 后 JSON 中 `output.text` 为 **累积全文**；通过比较 `fullResponse.length()` 与当前 `text.length()` 计算 **增量 chunk** 调用 `callback.onMessage`，实现增量推送。

异常时返回友好固定中文错误句，避免前端空白。

### 6.10 流式体验与 SSE 封装

**后端语义单元切分 `streamBySemanticUnits`**：对模型返回的每个 chunk 再遍历字符——**连续英文字母/数字/下划线/连字符** 攒成 **完整英文单词** 再一次性推送；**中日文等非 ASCII** 按单字符推送；每次推送后 **随机休眠约 60~100ms**，形成「打字机」节奏感。

**控制器 `AssistantController.chatStream`**：`SseEmitter` 超时 **60s**；响应头 `Cache-Control: no-cache`、`Connection: keep-alive`、`X-Accel-Buffering: no` 减轻代理缓冲。

**前端 `chatStreamPost`（`src/api/assistant.ts`）**：`fetch` POST JSON，**ReadableStream** 按行解析；`data:` 行若可 JSON 解析且含 `products` 则收集推荐商品；纯文本则直接追加到界面。流结束后父组件 `emit('send')` → `Assistant.vue` 重新 `loadMessages` 以展示 **落库后的完整消息与关联商品 ID**（历史接口再渲染 `ProductRecommendation`）。

**前端 `ChatWindow.vue`**：`el-switch` 切换 **流式 / 普通**；流式模式下用 `streamingMessage` 临时气泡 + Loading；普通模式显示「正在思考…」。用户消息采用 **乐观更新**（先插入本地 `optimisticMessages`）。

### 6.11 前端助手页面结构（答辩「界面模块」页）

- **`Assistant.vue`**：`el-row` 两栏——左侧 **会话列表**（`ConversationList`：选择、新建、删除），右侧 **聊天窗**（`ChatWindow`）。`currentSessionId` 变化时 `watch` 拉取 `/assistant/conversation/{sessionId}/messages`。新建会话时 `sessionId` 置空，消息清空，待首条发送后由后端返回新 `sessionId` 并刷新列表（具体以 `ChatWindow` 与父组件协同为准）。  
- **`ChatWindow.vue`**：消息区 + `MessageInput` + `ProductRecommendation`（展示 `relatedProducts` 解析后的对象需与后端返回字段一致；卡片点击 **`router.push(/products/:id)`** 进详情）。  
- **`ProductRecommendation.vue`**：网格展示图、名、价，风格与全局 CSS 变量一致（HUD 科技风文案为展示效果，答辩可改为更学术表述）。

### 6.12 入站内容治理：`ContentCheckInterceptor`

- 对 **`/assistant/chat`**、**`/assistant/chat/stream`**（以及预留的 `/comment`、`/admin/announcement`）在 `preHandle` 中读取 Body，解析 JSON 字段 **`message`**（助手）或 `content`。  
- 调用 `AIContentCheckService.isContentViolation`：`AIContentCheckServiceImpl` 构造 **另一套检测用 prompt**，调用 **同一 `LLMService`** 要求返回 JSON（`isViolation`、`violationType` 等），解析后若违规则 **直接 `Result.error` 拦截**，不进入助手主逻辑。

**注意**：助手聊天会 **额外消耗一次 LLM 调用** 做安检（成本与延迟需在答辩「展望」中可提及优化：关键词预过滤、小模型、异步抽检等）。

## 七、其他智能化能力（与助手并列的扩展）

- **管理端订单 AI 分析**：`POST /admin/orders/analysis/ai`，将统计指标与 `chartData` 摘要发给 `LLMService`，生成【结论】【问题】【建议】结构化运营文字。

- **客服模块**：`CustomerServiceController` 提供生成回复、模板与历史（与助手可形成「前台助手 + 后台客服辅助」叙事）。

## 八、安全与认证（全系统）

- **JWT**：`JwtInterceptor` 校验 `Authorization: Bearer`；未授权返回 JSON `401`。  
- **放行路径**：含 `/user/login`、`/user/register`、`/user/admin/login`、**`/assistant/**`**、`/error`。助手接口的认证策略见 **6.15**。  
- **密码**：BCrypt 等加密存储（Spring Security Crypto）。

## 九、部署运行（简表）
